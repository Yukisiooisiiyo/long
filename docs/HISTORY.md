# 判断の履歴：どういう考えで今の形に決めてきたか

設計・実装・検証の流れと、そのときどの選択肢を比べて何を基準に決めたかを、時間の順に残します。数値の詳細は [BENCHMARKS.md](BENCHMARKS.md) にあります。

## 0. 全体を通した方針

この4つは途中で何度も判断の基準になりました。

1. **正しさが最優先**：「最長」を求める問題なので、出す答えは常に厳密解にする。速くするための工夫も、厳密性を崩さない形に限る。
2. **出力の規定を守る**：標準出力には決められた形式以外を一切出さない。統計やエラーは標準エラーへ。
3. **計測してから採用する**：案は1つずつスイッチで切り替えられる形で入れ、対照実験で効果を確かめてから採否を決める。効かなかった案は、実行時に負担を残さないよう既定から外す（最終的にコードからも削除）。
4. **速さは目的ではなく手段**：評価してもらうための主な手段として速さを詰めたが、提出物としての読みやすさ・確かめやすさを崩してまでは追わない。

## 1. 問題の解釈と大方針

- **解釈**：駅＝頂点、路線＝重み付きの辺とした「最長単純路（＋最長閉路）」の問題。始点と終点が同じでもよいので、ループも答えの候補になる。
- **計算量の調査**：最長経路は NP 困難で、一般には指数時間がかかる。調べた範囲では、方法ごとに得意な入力の形がはっきり違った（木なら線形、小さい部分ならビットDP、細い形なら木幅DP、それ以外は分枝限定法）。
- **規模による分岐**：「駅の数で解き方を切り替えれば、分岐の手間より得の方が大きいのでは」という発想から出発した。結果として、判断の単位は「グラフ全体の駅数」ではなく「ブロック（1駅では切り離せない部分）ごとの大きさと形」にした。鉄道網は、小さいブロックが関節点でつながった形になりやすいため。
- **正しさか、何か答えを出すか**：問題の意図は「最長」を求めることなので、厳密解を既定とした。時間制限で打ち切る機能は、検討のうえ次の形にした。
  - 既定は無効（True/False で切り替え）
  - 時間切れのときは「エラーで止める」か「その時点の最良解を出す」かを選べる
  - どちらも出力の形式は変えない

## 2. 上界と初期解（設計段階）

- **枝刈り**：「どこまで伸ばしても今の最良を超えない枝は捨てる」ための上界として、残りの到達可能部分の合計、各駅の重い辺2本、関節点での枝分かれ（大きい方だけ数える）を組み合わせた。
- **初期解**：最初から良い解があるほど枝刈りが効くので、性質の違う方法を組み合わせた（貪欲法、最大全域木の直径、基本閉路、ビームサーチ、局所探索）。
  - 「ループ構造が長い経路になりそう」という直感から、基本閉路を種にする方法も入れた。
  - 「距離を重みとするニューラルネットワークのような図に見える」という発想から、ビームサーチ（候補を幅を決めて同時に伸ばす方法）を入れた。
- **ラグランジュ緩和**：「各駅の次数は2以下」という制約を罰金に移すと、最大全域森という簡単な問題で上界が求まる。罰金は入力を読んだ後に毎回調整する（事前学習ではない）。他の上界と併用でき、精度が下がることはない。計算量が増える分は、効果が薄いときに自動で切る仕組みで抑えた。

## 3. Python での対照実験

言語の速さの違いを除いて考えるため、まず Python で全パーツを実装し、1つずつ外して効果を測った。

- **効かなかったもの**
  - 鎖の圧縮（次数2の駅をまとめる）：かえって遅くなった。
  - 「ラグランジュ上界は浅い階層だけで使う」：誤りだった。全階層で使う方が速かった。
- **見つかった不具合**
  - 部分的な始点の扱い
  - ループの探索で経路用の上界を流用していたこと
  - 探索の根でのラグランジュ上界の使い方
  - 到達可能性と関節点を同時に求める走査での、始点への戻り辺の扱い

  いずれも総当たりとの照合で見つけて直した。この「別の方法と照合する」形のテストを、以後ずっと続けている。

## 4. C++ への移植

- **言語の選択**：アセンブリなども検討した。正確性を前提に最速を目指し、かつ自分で安全に実装・検証できることを重視して C++20 にした。
- **鉄道網3,000駅が遅い（4.4秒）**：調べると、大きいブロックが関節点ごとに探索をやり直していた。
  - 「関節点の先で稼げる距離を端のおまけとして扱う」方法に変え、1ブロックの探索を3回だけにした。
  - おまけを考えた初期解も加えた（遅さの93%は、良い解を見つけるまでの時間だったため）。
  - 4.4秒 → 0.3秒になった。
- **7つの案の対照実験**：始点の順番、ループ専用の乗数、番号の付け直し（軽い駅から）の3つを採用し、合計で約4.9倍速くなった。
  - 「ループの向きを1つに絞る」：探索の記録が効かなくなり、逆効果だった。
  - 「ループ探索の分担を細かくする」：2コアの環境では効かなかった。
  - 照合テストで、分担を細かくする案に誤りを1つ見つけて直した。
- **起動の短縮**：例題（駅4つ）の実行時間の大半はOSの起動だった。静的リンクと「小さいグラフは1スレッド」で、2.4ミリ秒 → 1.3ミリ秒にした。

## 5. 規模を変えた計測で弱点を探す

「規模ごとの処理時間から弱点を分析したい」という目的で、5種類の形を小規模から大規模まで計測した（`bench/sweep.py`）。

- 時間を決めるのは駅の数ではなく、**一番大きいブロックの大きさと形**だった。
- 時間切れしたブロックは、どれも「細くて長い」（木幅4以下で独立したループが100個以上）ものだった。分枝限定法はこの形に弱い。

## 6. フロンティアDP（細いブロック）

- 細い形には、端から順に処理する動的計画法が合う。既存の分解（端のおまけ・端の固定・ループ）と組み合わせられることを確かめてから実装した。
- 状態が多すぎるときは諦めて分枝限定法に戻す形にし、どちらに転んでも厳密解が出るようにした。
- 時間切れしていた鉄道網（1,000〜5,000駅）と細長い格子が、0.1秒以内で解けるようになった。
- 一方で、密集したグラフは幅が小さくても状態が爆発した（18駅で1ステップ740万状態）。そこで「密集なら使わない」条件を計測から決めた。

## 7. 大きな格子と密集グラフ

- **格子11×11**：状態の大半は答えに届かないものだった。
  - 状態ごとの上界で捨てる方法と、絞ったDPで先に良い解を作る方法（ビーム）を加えた。
  - 「時間切れ」が0.23秒になった。ビームの幅は6通り比べて1,000に決めた。
- **密集48駅（15秒）**：時間の大半は「これ以上長いループはない」ことの証明だった。
  - 最良解を最初に与えても11秒かかったので、初期解ではなく上界の問題だと判断した。
  - 始点ごと・最初の数歩ごとに乗数を調整し直す「ラグランジュ分岐」を入れ、1.3秒になった。
  - 良いループを先に作る局所探索も試したが、ラグランジュ分岐の後では効果がなく、小さい入力で遅くなったので外した。
- **時間制限の超過**：計測中に、制限を最大5秒超えることに気づいた。
  - 原因は、時刻を確認する間隔と、大きな記録表の解放の2つだった。
  - 両方を直し、超過は0.03秒以内になった。

## 8. 時間の内訳を測ってからの改良

「1/100にしたい」という目標に対し、まず次の見積もりをした。

- 並列化はコア数分の1が上限。
- コンパイラの調整は1/1.1〜1/1.5程度。
- 実際に効くのはアルゴリズムの工夫だけ。

そのうえで、プロファイラ（callgrind）で時間の内訳を測り、内訳に合わせて案を選んだ。

- **普段の入力**：時間の約半分が小さいブロックのビットDP、2割弱が入力の読み込みだった。
  - ループだけのブロックの公式、全経路の列挙、答えの経路を最後に1回だけ組み立てる、などの7つを入れ、2〜6倍速くなった。7つとも、1つずつ抜くと遅くなることを確かめた。
  - **鎖の圧縮は実装しなかった**。計算すると、消せる処理は大きいブロックの辺の2割程度で、上限でも全体の1割程度だった。経路の端が鎖の途中に来る場合の扱いが複雑で、正しさの危険に見合わない。
- **格子**：
  - ランクベース法を実装したところ、正しく動いたが、枝刈りの後ではほとんど効かず遅くなった。状態が50万を超えたときだけ使う設定にした。それ以下では何もしないので負担はない。
  - **木分解DPは実装しなかった**。格子では効果がない（木幅＝今の幅）ことが分かっていたため。
- **密集**：
  - LP（線形計画）の上界を Python で試作し、今の上界よりずっと締まる（最適との差が1/5）こと、証明に必要な探索が17ステップ程度であることを確かめてから C++ で実装した。
  - 正しさが自作の単体法の正確さに依存しないよう、次の3点を守った。
    - 枝を捨てる判断は「どんな双対でも成り立つ形の上界」でだけ行う。
    - 「解なし」は検算できたときだけ採用する。
    - 見つけた解は元のグラフで測り直す。
  - 密集24入力の合計が13.6秒 → 3.4秒、最悪27秒 → 0.21秒になった。
  - 経路探索にもラグランジュ分岐を入れた（LPが諦めたときの予備）。
  - ループの向きの重複除去は、速くなる入力と遅くなる入力が混在したので不採用にした。

## 9. 提出に向けた整理

速さは評価のための主な手段であり、目的ではない。速さを崩さない範囲で、提出物としての完成度を上げる方針に切り替えた。

- **コード**：既定で使わなくなった実験用の分岐と、古い実装（置き換え前の入力読み込みやブロック処理など）を削除した。調整用の設定は、照合や計測に意味のあるものだけ残した。
  - ソースは4,802行から4,063行になった。
  - 削除前後を比べ、計測用の111入力のうち109入力で出力がバイト単位で同じだった。残る2つは、削除前の版も30秒で終わらない格子14×14。
  - 速さに差はなかった（再計測で同じ時間）。
  - 照合テスト（約4,800回と大きい入力30個）は全て一致した。
  - 実験当時のコードは別の圧縮ファイル（`longest_cpp_experiments.zip`）に残してある。
- **文書**：README は「使い方・解き方の概要・正しさの確かめ方」に絞った。詳細は DESIGN、計測は BENCHMARKS、経緯はこのファイルに分けた。

## 10. このプログラム専用の最適化

「コンパイラを今回のプログラム用に最適化する」案は効果が小さいとして一度は消えた。ただ、「汎用の道具が知らない、このプログラムと入力の性質を使う」という視点で見直すと、別の候補が出てきた。

- **メモリ確保**：汎用の malloc は、いつ解放されるか分からない前提で作られている。このプログラムは小さい一時データを大量に作っては捨てる。専用の確保の仕組みで約1割速くなった。
- **フロンティアの幅**：コンパイラは実行時の幅を知らない。幅が12以下なら状態を1語で持つ版を用意し、4〜11%速くなった。
- **距離の整数化**：入力の距離は小数2桁程度の値だと分かっているので、整数にして計算する。速さはほぼ変わらなかったが、検証の過程で、合計が非常に大きいとき0.01の差を見落とす不具合が見つかった。これは採用の決め手になった。「速さより正しさ」の方針に一番合う結果だった。
- **効かなかったもの**：
  - PGO（数%、ビルドが2段階になる）
  - CPUごとの関数の作り分け
  - 終了時の後片付けの省略
  - 起動の固定費の削減
  - 分枝限定法の作り分け（今の既定構成では効く先がない）

  見積もりどおり、ハードウェアや起動まわりの最適化はほぼ効かないことを、計測で確かめた。

## 11. 難問を速く解く方向へ

細かい区間ごとに方法を割り当て直す案も考えたが、過剰適合と照合の手間が増えるわりに伸びしろが小さいと判断し、見送った。代わりに「今は解けない難問を解けるようにする」方向に進んだ。

- **まず難問セットを作って測った**：格子（14×14〜20×20）、120駅を超える密集、中くらいの密度のランダムグラフの45入力で、20秒以内に解けたのは17入力だった。
- **中くらいの密度が一番の弱点だった**：細くないのでフロンティアDPが使えず、LPの条件からも外れて、分枝限定法だけに頼っていた。
- **LPを「フロンティアDPが受け持たない全ブロック」に広げた**：端のおまけと端の固定はLPの形でそのまま表せたので、他とつながったブロックにも使えた。
- **広げる過程で見つかった問題を、1つずつ測って直した**：
  - 制約の上限に当たって証明を諦めていた
  - 最小カットの計算が密な表で遅かった
  - 単体法のピボットが重かった
  - LPの前の初期解作り（ビームサーチ）が時間の96%を占めていた
  - LPが時間制限を確かめていなかった
- **効かなかった案**：格子の白黒の釣り合い（LPの解は元から釣り合っていた）、被約費用による辺の固定。どちらも測ってから外した。
- **結果**：難問セットで36/45が解けるようになった。密集グラフは80駅でも0.05秒以内になった。
- **残った難問**（格子16×16以上など）は単体法の表の大きさが壁で、表を密に持たない改訂単体法が次の一手になる（→12節）。

## 12. 改訂単体法

LPを広げた後の難問は、単体法の表の大きさが壁だった。まず時間を測ると、表の更新が7割、基底変数の値の計算が2割で、単体法が9割を占めていた。そこで、表を持たずに元の疎な行列と基底の逆行列（積形式）だけを持つ改訂単体法を自作した。

- 実装は表方式と同じ入口にそろえ、スイッチで切り替えて同じ問題を解かせ、比べられるようにした。
- 実装中に不具合が2つ見つかった。どちらも照合とアドレスサニタイザーで見つけて直した。表方式のときから「単体法が間違っても答えは間違えない」設計にしてあったので、不具合の症状は「証明を諦めて遅くなる」で、間違った答えは出なかった。
- 難問のLPは合計86秒 → 15秒、最悪35秒 → 3秒になった。
- LPが速くなったことで、広い格子ではフロンティアDPよりLPが速くなった。そこで方法の順番を見直し、境目は計測で決めた（幅14まではDP、それより広いとLPが先）。
- 難問セットは41/45が解けるようになった。表方式の単体法は、照合用の独立した実装として残した。
